# Roster UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build roster's SPA — every screen in the design handoff — by harvesting an existing React codebase for the parts that earn their place, wiring the screens that have a backend to the live API, and backing the rest with schema-accurate mocks until their endpoints exist.

**Architecture:** React 18 + Vite + Tailwind 4 talking to `localhost:8000`. React Query owns server state, React Router owns navigation, MSW owns the mock boundary. `app/` holds the shell, `modules/` holds feature slices, `components/ui/` holds design-system primitives, `lib/api/` holds the typed envelope client and the capability registry that records what is real.

**Tech Stack:** React 18, TypeScript (strict), Vite 5, Tailwind 4, React Query v5, React Router v6, MSW v2, Vitest 2, Testing Library, pnpm.

**Design source of truth:** [`docs/design/README.md`](../../design/README.md) and the hi-fi canvas beside it. Exact tokens, dimensions, and per-screen specifications live there — this plan references sections rather than duplicating values. **The hi-fi canvas is the visual authority; where this plan and the handoff disagree, the handoff wins.**

**Spec:** [`docs/specs/2026-08-01-roster-design.md`](../../specs/2026-08-01-roster-design.md). §6 covers the frontend. **Where the spec and this plan disagree, the spec wins — stop and flag it.**

## What is actually true on `main` today

This plan was written against the merged backend, not an earlier draft of it. Verify rather than assume, but these are the facts it is built on:

**Layering.** `projects/server/src/{domain,adapters,interactors,config}`. The API lives at `interactors/api/`, the app factory is `interactors.api.app:create_app`, and database access goes through a Repository + UnitOfWork.

**Routes mount at the root — there is no `/api` prefix.** `create_app` includes each router directly, so the live paths are `/projects`, `/work-items`, `/agents`. The UI client uses a `/api` base, so **the Vite dev proxy must strip the prefix**. Getting this wrong produces 404s that look like backend faults.

**The envelope** is `{success, data, error}` plus `meta: {total, page_size, page_number}` on collections. 204s have no body.

**Fields are `snake_case`** (`project_id`, `folder_path`, `epic_id`). The UI mirrors the API exactly and does **not** camel-case at the boundary — one vocabulary, no mapping layer to drift.

**`make dev` already exists** as `db-upgrade seed run` and starts the API only. Task 14 adds the UI to it. `make install` already installs `projects/ui` when that directory exists, so it needs no change.

### Endpoints that exist

| Method | Path | Notes |
|---|---|---|
| `GET`/`POST` | `/projects` | list unpaginated (`page_size=0` fetches all), ordered by name |
| `GET`/`DELETE` | `/projects/{id}` | delete returns 204, no body |
| `GET` | `/work-items?project_id=` | **`project_id` is required** — there is no all-projects listing |
| `POST` | `/work-items` | |
| `PATCH` | `/work-items/{id}` | 409 illegal transition, 422 invalid value |
| `GET` | `/agents` | read-only; `status` is `working` while that agent has an in-flight turn |
| `GET`/`POST` | `/threads` | filters `project_id`, `work_item_id`, `status`; listing carries derived `message_count`, `last_message`, `participants` |
| `GET`/`PATCH` | `/threads/{id}` | 409 on an illegal status move, 422 on a malformed one |
| `GET`/`POST` | `/threads/{id}/messages` | posting with `agent_name` starts that agent's turn |
| `POST` | `/threads/mark-all-read` | |
| `GET` | `/threads/{id}/stream` | SSE; each message arrives as `event: <kind>`, closes when the thread resolves |
| `GET` | `/projects/{id}/memory`, `/memory/journal`, `/memory/snapshots` | |
| `POST` | `/projects/{id}/memory/compact`, `/memory/snapshots/{name}/restore` | |

### There are no run endpoints

Runs were removed from the code entirely (spec decisions 16–18, PR #2). There is nothing left to accidentally consume — but the constraint below still stands, because the *vocabulary* must not come back through the harvested code: no run entity, route, hook, or type, and no run monitor. Live agent output is read in the Thread tab, which is now genuinely live.

### No CI exists yet

There is no `.github/workflows` directory at all. Task 14 creates the workflow from scratch with **both** a backend job and a UI job — there is no existing backend job to match.

## Global Constraints

Every task's requirements implicitly include this section.

- **pnpm only.** Never `npm` or `yarn`. All commands run from `projects/ui`.
- **TypeScript strict.** No `any`, no `@ts-ignore`. If a type is genuinely unknown, `unknown` plus a narrowing check.
- **`pnpm lint` (eslint + `tsc --noEmit`) and `pnpm test` green before every commit.**
- **Types mirror the API**: `snake_case`, no camel-casing layer.
- **Design tokens come from the Tailwind theme.** A literal `#7c6cf0` in a component is a defect.
- **Mock-first:** `VITE_USE_MOCKS=true` is the default and the whole app must run with no backend.
- **Every screen handles loading, empty, and error states.** A screen with only a happy path is incomplete.
- **No run vocabulary** in any route, component, hook, type, fixture, or test name — spec §6.
- Tests use AAA structure with descriptive behaviour names, querying by role or label where an accessible query works.
- Commit format `<type>: <description>`. No attribution trailers.
- The string `naaf` must not appear anywhere under `projects/ui` after Task 1.

## The capability registry — how this plan stays honest

Several designed screens still have no backend, and the boundary **runs through screens, not between them**: the Board's work items and assigned agent are live while the token count on the very same card is not.

A screen-keyed registry would therefore lie about exactly the screens where the lie is most expensive. So provenance is keyed by **capability** — a named unit of data — and a screen's badge is the union of what it consumes. Un-mocking is deleting a file from `src/mocks/unbacked/`, which the test in Task 3 then forces the registry to reflect.

| Capability | Status | Why |
|---|---|---|
| `projects.list` / `.create` / `.delete` | live | `/projects` |
| `projects.itemCount` | unbacked | `Project` has no `item_count`; derived client-side |
| `workItems.listByProject` / `.create` / `.update` | live | `/work-items` |
| `workItems.readOne` | unbacked | no `GET /work-items/{id}`; detail reads from the project listing |
| `workItems.assignedAgent` | live | `WorkItem.agent_name` |
| `agents.list` | live | `GET /agents` |
| `agents.workingStatus` | live | an in-flight turn is the only source of `working` |
| `agents.write` | unbacked | no agent write endpoints |
| `memory.read` | live | `GET /projects/{id}/memory` |
| `threads.list` / `.messages` / `.post` / `.resolve` | live | `/threads` and its message routes |
| `threads.stream` | live | `GET /threads/{id}/stream` |
| `tokens.usage` | unbacked | **no token, spend, or progress field exists on any entity** |
| `mcp.servers` / `.detail` | unbacked | no `McpServer` |
| `attachments.list` / `.upload` | unbacked | no `Attachment` |
| `secrets.list` | unbacked | no `Secret` |

export function screenProvenance(screen: ScreenKey): {
  live: boolean;
  unbacked: CapabilityKey[];

import { http, HttpResponse } from "msw";

import type { Agent } from "../lib/api/agents";
import type { Message } from "../lib/api/threads";
import type { WorkItem } from "../lib/api/workItems";

const envelope = <T,>(data: T) => ({ success: true, data, error: null });

const list = <T,>(items: T[]) => ({
  ...envelope(items),
  meta: { total: items.length, page_size: 50, page_number: 1 },
});

  HttpResponse.json({ success: false, data: null, error }, { status });

export const workItemsHandler = (items: Partial<WorkItem>[]) =>
  http.get("/api/work-items", () => HttpResponse.json(list(items)));

export const workItemsError = (status: number) =>
  http.get("/api/work-items", () => failure(status, "could not load work items"));

export const workItemPatchError = (status: number, error: string) =>
  http.patch("/api/work-items/:id", () => failure(status, error));

export const agentsHandler = (agents: Partial<Agent>[]) =>
  http.get("/api/agents", () => HttpResponse.json(list(agents)));

export const agentsError = (status: number) =>
  http.get("/api/agents", () => failure(status, "could not load agents"));

export const threadMessagesHandler = (messages: Partial<Message>[]) =>
  http.get("/api/threads/:id/messages", () => HttpResponse.json(list(messages)));
